# Business Rules

## Core principle

The backend is authoritative. The browser may collect input, but it must not decide customer ownership, product identity, approval rights, or final status.

## Warehouse registration and dispatch

1. Warehouse staff create one consignment record per tire serial number.
2. `consignment_item_id` is generated by the backend.
3. `serial_num` must identify one tire uniquely.
4. Customer and product values are resolved before shipment and stored as snapshots.
5. A newly registered tire starts with `inventory_status = READY_TO_SHIP`.
6. No driver or warehouse worker is required to click a `SHIPPED` status in
   the first version.
7. Rows are never deleted. Invalid records become `VOID`.

## Sugar-mill receiving

1. The checker signs in with an active account where `can_receive = TRUE`.
2. The checker scans every tire QR code with the USB-C 2D scanner.
3. No ORD paper is required at the sugar mill.
4. The backend resolves the serial to the consignment item.
5. A valid `READY_TO_SHIP` item becomes `RECEIVED`.
6. The receiving account must match the customer assigned to the consignment
   item, unless an explicitly authorized internal receiving workflow is added.
7. Every scan attempt is recorded in `LOG : รับเข้าสินค้าฝากขาย`.
8. A duplicate scan is rejected and recorded as `DUPLICATE`.
9. Unknown, wrong-customer, or already-withdrawn serials are rejected.
10. A serial is normalized to uppercase and must contain exactly 10 English
    letters or digits. Letter and digit positions may vary, and either type may
    appear alone, for example `TN05200154`.
11. Every scan has a stable client request ID. Retrying the same request returns
    the original result without creating another log row. Reusing that ID for
    a different user, batch, or serial is rejected as a conflict.
12. A user may receive only inventory assigned to their `customer_id`. An
    internal account with both `can_receive = TRUE` and `is_admin = TRUE` may
    receive across customers for controlled support.
13. The backend uses a short script lock and re-reads the inventory row before
    changing `READY_TO_SHIP` to `RECEIVED`.

## Customer withdrawal

1. The customer signs in with Google.
2. The customer scans one or more serial numbers into one withdrawal batch and
   submits each serial with its required photo.
3. The backend obtains the email from the verified Google ID token.
4. The backend maps the email to `CONFIG : อีเมลที่ได้รับสิทธิ์`.
5. The backend confirms that the serial belongs to that customer.
6. The backend pulls ORD, lot, and product values from the consignment record.
7. The photo is uploaded to the company Drive or Shared Drive.
8. The photo must upload successfully before the final withdrawal submission.
   The backend verifies that it is an image in the configured company
   withdrawal-photo folder; a browser-provided file ID is not trusted alone.
9. The browser resizes each photo to a maximum dimension of 1600 pixels and
   converts it to JPEG before upload. The backend rejects invalid JPEG data or
   decoded files larger than 5 MB.
10. Shared Drive uploads use the Advanced Drive service with
    `supportsAllDrives = TRUE` and a backend-generated filename. If the
    deployed runtime has not propagated Advanced Drive create authorization,
    the backend may use the configured Drive folder service as a fallback.
11. Every photo upload has a stable `photo_upload_id`. Retrying the same upload
    returns the existing Drive file instead of creating a duplicate image.
12. All serials submitted together share one `withdrawal_batch_id`.
13. Under a short script lock, the backend rechecks each current inventory row,
    writes one withdrawal row per serial, and changes `RECEIVED` to `WITHDRAWN`.
14. The customer can use the tire immediately after a successful submission;
    no Admin approval is required beforehand.
15. Each withdrawal row is written with `request_status = SUBMITTED`.
16. The backend sends one grouped Google Chat notification for the batch after
    the withdrawal rows are saved successfully.
17. A retry with the same `client_request_id` must not create a duplicate
    withdrawal.
18. The batch is all-or-nothing: if any serial, ownership, status, or photo
    validation fails, no inventory row changes to `WITHDRAWN`.

## Google Chat order notification

1. The notification groups rows by `withdrawal_batch_id` and `customer_id`.
2. Product lines are grouped by `product_code` and `product_name_snapshot`,
   with quantity calculated by the backend.
3. The card contains customer code/name, grouped products and quantities,
   total quantity, submission time, and a link to the Admin web-app request.
4. Photos and the full serial list are not embedded in the Chat card. Admin
   reviews those details inside the authenticated web app.
5. One batch creates one Chat notification, not one message per tire.
6. If Chat delivery fails, the withdrawal rows remain `SUBMITTED` and only
   `chat_notification_status` becomes `FAILED` for retry.

## Admin ERP confirmation

1. Only an authenticated user with `is_admin = TRUE` and `is_active = TRUE`
   can access ERP-confirmation actions.
2. The Admin page may be in the same web app as customer pages.
3. Google Chat sends a link to the Admin page; the link itself does not grant
   confirmation permission.
4. ERP confirmation is a backend POST action, not a URL action.
5. The Admin checks the separate ERP system outside this application.
6. The Admin page provides one `APPROVED` action; no in-app checklist or ERP
   integration is required for the first version.
7. An Admin can confirm only a request currently in `SUBMITTED` status.
8. Confirmation records the Admin identity and timestamp in the existing
   `approved_by_*` and `approved_at` columns.
9. `APPROVED` means the ERP order was completed; it does not authorize the
   physical withdrawal.
10. A request that is not ready for ERP confirmation remains `SUBMITTED`.

## Permission-based navigation

1. Users do not choose their permissions in the browser.
2. The backend returns `can_withdraw`, `can_receive`, and `is_admin` for the
   verified email.
3. The frontend displays every mode allowed by those permissions.
4. Hiding a mode in the frontend never replaces backend authorization.

## Authorized-account management

1. Only an active account with `is_admin = TRUE` may list, create, edit,
   activate, or deactivate accounts.
2. Customer operational permissions are linked to a valid `customer_id` selected from
   `MASTER : Customer`; the admin must not type an arbitrary customer ID.
3. An internal account with `is_admin = TRUE` is not linked to a customer.
4. Email addresses are normalized to lowercase and must be unique.
5. Accounts are never deleted. Revoked access sets `is_active = FALSE` and
   records `updated_at` and `updated_by`.
6. An admin may update an existing account's permissions and linked customer,
   but the Google email remains immutable.
7. An admin cannot deactivate or change the access of the account currently
   being used.
8. Account creation, access changes, and status changes use a script lock around the final
   read-check-write operation.

## Status and deletion

- Do not call `deleteRow()` for business records.
- Use `VOID`, `CANCELLED`, or `REJECTED` according to the record type.
- Status transitions must be validated by the backend.
- A previously withdrawn record cannot be silently processed again.

## Concurrency

- Use `LockService.getScriptLock()` around short read-check-write sections.
- Re-read the current row inside the lock before changing its status.
- Do not hold a lock during Drive uploads, Chat notifications, or other slow network operations.
- Use `client_request_id` to make retries idempotent.
- A duplicate request returns the existing transaction instead of creating a second one.

## Notifications

- Write the transaction before sending a Chat notification.
- Chat notification failure must not remove the transaction.
- Store notification status and retry information in the transaction row.
- Keep webhook URLs in Apps Script Script Properties, never in source code.

## Internet limitations

The first version requires an internet connection for authentication, lookup, Sheet updates, and Drive uploads. The UI must show a clear failure state and must not create duplicate records when a request is retried.
